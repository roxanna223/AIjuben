## 二、分阶段详解

### 阶段一：基建与上线（v0.1.x · 2026-08-27）

**问题 1：小内存服务器 vs 会话驻留内存**
- 现象：阿里云 2G 内存 ECS，会话全量驻留内存会吃爆。
- 方案：`SESSIONS` 改 OrderedDict LRU——上限 256（`MAX_MEM_SESSIONS` 可调），超限淘汰最久未用（先落盘再淘汰，访问时自动从磁盘读回）。

**问题 2/3/4：部署杂症**
- 备份 cron 静默失败 → 改用 `/etc/cron.d/qilu-backup`；
- 打包带入 `._*` 元数据 → 打包规则排除；
- 首次部署 SSH 交互 → SSH_ASKPASS 装公钥后免密。

### 阶段二：开局体验与安全（v0.2.x · 2026-08-27）

**问题 5：开局 10~30 秒无反馈 + 连点重复开局烧 token**
- 根因：LLM 生成开场期间页面无反馈，用户误以为卡死反复点击，每次都真实建会话。
- 方案：三层防线——① 点击剧本立即切"加载中"过渡页（按钮随页面隐藏，点不到）；② 前端 `enteringStory` 防抖；③ 开局接口独立限流 20 次/分/IP。
- 经验：**昂贵操作的入口要同时做"视觉反馈 + 前端防抖 + 服务端限流"**。

**问题 6：打开网站被自动续玩拉进故事，选故事页被跳过**
- 方案：移除页面加载时的自动 `resume()`；选故事页顶部显示「↻ 继续上次的故事」卡片（显示进度），点击后走同样加载过渡页。
- 经验：**恢复（resume）要显式、要展示进度，不替用户做决定**。

（同阶段顺手完成的安全加固：IP 限流、管理接口令牌鉴权、行为事件采集+IP 脱敏、nginx 安全头。）

### 阶段三：小说体 → 人物对话体（v0.3.x · 2026-08-28）

**问题 7：小说体呈现不符合文字游戏**
- 现象：正文是一整段小说体 `narrative`，读起来像看小说。
- 方案：数据模型升级为结构化 `dialogue` 数组 `[{speaker, text}]`（speaker=人物ID 或 narrator 旁白）——说话人与台词分离，前端按角色渲染名字/头像气泡（NPC 左、主角右、旁白居中），流式"完成一行推一行"；两个剧本 mock 正文全部改写为对话体。

**问题 8：人物图片需求 vs token 成本**
- 需求：每个角色要配图嵌进对话；约束：不消耗图片模型 token。
- 方案：代码手绘扁平风 SVG 矢量头像（每角色 ~2KB），带标志元素（林sir警徽/小满缺角怀表/葛姨茶叶蛋/老周钥匙串/阿禾长发/主角金星）；`AVATAR_IMAGES` 按角色ID登记，后续换成 AI 生图只需换文件路径、代码零改动。
- 经验：**能用确定性代码产出的资源，就不要用生成模型**。

**问题 9：场景写过长被驳回 → 先流式后重绘 + 双倍 token**
- 现象：真实模型带上下文时把场景写到 900+ 字，被审查器驳回重写——前端先把第一稿流式播放、done 时又被替换，观感差且同回合两次生成。
- 方案：提示词明确"总行数/字数"目标；修复后流式行与最终稿 100% 一致（12=12）。
- 经验：**提示词里给出的篇幅目标要写进铁律，并与审查阈值对齐**。

**问题 10：旧存档/旧脚本兼容**
- 方案：`as_dialogue_lines()` 归一化——旧 `narrative` 字符串自动变单条 narrator 行，老会话无缝续玩。

### 阶段四：游戏化交互（v0.4.0~v0.4.2 · 2026-08-28）

**问题 11：需要"每次只显示一句"+自动播放**
- 方案：前端逐句播放器 `Player`（状态机 idle/typing/wait）——打字中点击=补全本句、再点=下一句；空格同效；自动播放按文本长度放慢（2~5.5s/句）、**到选项处自动暂停**、选完后新场景自动继续。

**问题 12/13：输入内容 UI 不对齐 + "输入了没用"**
- 现象：选项与自由输入渲染成右下角无头像灰条；输入框全程可见但剧情对自由输入响应弱。
- 方案：① 玩家发言统一渲染为带头像的「你」气泡（选项带"»"前缀）；② 输入区**仅在交互点（选项出现时）显示**，播放/生成期间自动收起，生成失败自动恢复上一交互点；③ 引擎侧把自由输入升级为"玩家刚刚的自主行动/发言（必须让在场人物明确回应）"。
- 验证：真实 LLM 实测输入"我示意林sir继续说下去"→ 下一场开头林sir立刻开口继续讲。

**问题 14：选项频率偏低**
- 方案：每场对白（非旁白）严格 5~6 行、旁白不计入、审查器对 >8 行驳回；每场 3~4 个选项。

**问题 15：选项与剧情衔接差——"选了一个选项≈没选"**
- 现象：选项"示意某人继续讲下去"，下一场对方却没开口；剧情由节拍表主导，选择只被当附加信息。
- 方案（三层）：① 写作契约——本场开头 2~4 行必须先承接选择（被示意的人先开口、选的行动先发生）再过渡节拍；② 审查兜底——一致性审查新增"选择承接检查"，无视选择输出 `choice_ignored` 驳回重写（复用既有 LLM 调用，零新增成本）；③ 后果可视化——选项气泡与新场景之间插入「✦ 影响」行（数值/倾向/事实变化+原因）。

### 阶段五：稳定性与确定性（v0.4.3~v0.4.8 · 2026-08-28）

**问题 16（BUG-001）：频繁"生成异常"，点继续后剧情接不上** → 详见 `06-Bug记录与修复.md` BUG-001。
- 根因三条：失败节拍被 `mark_done` 吞掉（主因）；提示词"对白 5~6 行"与"250~450 字"约束冲突致模型写 95~112 字超短场景被连续驳回（诱因）；模型把倾向写进 effects 的 stat 目标被静默丢弃（次要）。
- 方案：失败不吞节拍（`_fallback` 标记 + 导演 active 节拍优先重试 + 按钮改「重试」）；重写篇幅铁律（≥250 字、每行 15~60 字、2~4 行旁白补足）；审查器补选项 effects 的 stat 目标校验。
- 验证：连续 5 回合真实生成 0 兜底 0 降级。

**问题 17：刷新重进后"第一站消失的人"每次都变**
- 现象：用户不可操作的基础剧情被 AI 每次现编——跨局漂移、浪费 token、故事骨架动摇。
- 需求：基础剧情固定下来且有**依据**；依据成立则必然触发；只有玩家改变依据才产生变数。
- 方案：宪法新增 `fixed_plot` 固定剧情锚点 `{id, beat, fact, basis?, mutable_by?}`——导演以"【固定剧情·基础设定，不得改写】fact；依据；变数"注入编剧指令，一致性审查同步校验。配置《午夜列车》5 条（第一站消失者=沈阿婆/钟停 0:47/名册红圈机制/小满怀表/葛姨茶叶蛋）、《规则楼》3 条；mock 同步。
- 验证：两个独立会话 b2 均稳定出现"沈阿婆"（名册红圈依据）。

**问题 18：缺乏路线可视化** → v0.4.5 故事导图：渐进解锁的思维导图（到达过的节点才点亮、岔路空心占位防剧透、自由输入自创节点、随存档持久化）。

**问题 19（BUG-002）：服务重启后恢复存档第一回合崩溃，前端无限卡"编剧正在书写"** → 详见 BUG-002。
- 根因：`_active_beat` 只在 `_generate()` 赋值、`__init__` 未初始化（恢复会话直接进 `turn()` 触发 AttributeError）；流式 worker 只捕获 ValueError/RuntimeError，异常杀死线程、NDJSON 流永不结束。
- 方案：初始化 `_active_beat=None` + 从 `beat_status` 推导 active 节拍（兜底场景除外）；worker 加 `except Exception` 兜底回传 error 事件；旧存档导图回填。
- 经验：**状态恢复路径（重启/换机器）必须显式回归测试**；**后台线程必须兜住一切异常并回传事件，否则前端无限挂起**。

**问题 20（BUG-003）：数值/事实提前触发，未到剧情点就结算** → 详见 BUG-003。
- 现象：第一节拍选"检查物品"（乘客尚未消失）却结算"目睹乘客消失→理智下降"；甚至提前授予 b3 才应授予的 `f_ledger_confirmed`。全库 522 会话扫描 16 个受影响；后续审计发现历史违规：midnight-train 190 会话 316 条、rule-tower 79 会话 160 条。
- 方案：审查器硬防线（其他节拍的保留事实禁止提前授予）+ 提示词铁律强化 + 一致性审查 `effect_unjustified` + 前端「✦ 影响」分时展示（"✦ 你的选择"在选择后、"✦ 剧情推进"在剧情播完后）+ 污染会话数据修复。

**问题 21：校验逻辑散落 if-else，不可复用** → v0.4.8 ValidationScale 工程化校验框架（详见 `07-工程化校验框架.md`）：
- 原子单位=一次变化+上下文；9 条内置规则插件（数值合法性/剧情合法性/数值出发点/剧情出发点/语义一致性）；宪法 `validation` 段声明剧情点白名单/幅度上限/事实出处，口径按剧本自动装配；构建期（mock 全量校验）/运行期（每场即时校验）/审计期（历史会话离线扫描）三用；结构化报告 error→驳回、warn→记账。

## 五、方法论沉淀（贯穿全程的 6 条经验）

1. **提示词约束必须自洽**：v0.4.1 的"行数"与"字数"冲突直接酿成 BUG-001——每次加新铁律，先和既有铁律、审查阈值对齐（教训来自问题 9/16）；
2. **失败不能吞状态**：生成失败时节的"状态机"不能推进（BUG-001 主因）；同理恢复路径的状态必须显式初始化与推导（BUG-002）——**异常路径与正常路径要同等对待**；
3. **确定性优先于提示词自觉**：能写进宪法/代码的约束就不要指望模型自觉——`fixed_plot`（跨局一致）、节拍保留事实硬防线（BUG-003）、ValidationScale（校验工程化）是同一条原则的三次递进；
4. **后台线程必须兜住一切异常**并回传事件，否则前端无限挂起（BUG-002 放大器）；
5. **每个修复配三层验证**：回归测试（unittest）+ 真实 LLM 实测（双剧本走查/连续回合）+ headless Chrome UI 实测——本项目 81 项测试与各版本实测记录都是这一条的产物；
6. **文档三件套联动**：`05` 记版本条目（现象/方案/测试/部署）、`06` 记 bug 明细（现象/复现/根因/修复/遗留）、本文件 `08` 做全量总览——新问题按此登记，复盘不靠回忆。
