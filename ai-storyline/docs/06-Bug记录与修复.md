# Bug 记录与修复

> 本文件记录项目中发现的 bug、根因分析与修复方式，是排查与复盘的第一手资料。
>
> **使用规则：**
> 1. 每个 bug 一条记录，编号 BUG-XXX 递增；
> 2. 「修复方式」记录的是**当前采用的方案，不代表最优解**——如后续找到更好的修复方式（更健壮 / 更简单 / 更省成本），在原记录的「遗留风险 / 后续可改进」小节追加说明，并标注日期与版本；
> 3. 涉及代码变更时，同步在迭代文档（`05-迭代文档.md`）追加版本条目，并提交代码；
> 4. 状态字段：`已修复` / `部分修复` / `已知未修`。

## BUG-001 生成异常后剧情断裂（失败节拍被吞）

- **状态**：已修复
- **发现时间 / 版本**：2026-08-28 / v0.4.2
- **修复时间 / 版本 / 提交**：2026-08-28 / v0.4.3 / `4801693`
- **关联迭代记录**：`docs/05-迭代文档.md` v0.4.3

### 现象

用户报告：游玩中途多次出现"生成异常"提示，点击"继续"后剧情接不上，中间段落像被跳过了。

会话数据 `s_dfacb196` 佐证：

- 节拍路径只剩 `b1 → b2 → b4 → b6`，中间节拍内容缺失；
- `fallback_flags` 记录了 3 次 `generation_fallback`（驳回原因均为"正文过短：95~112 字"）；
- 另有一条 `choice_settle_partial: 未定义的数值 curiosity`。

### 复现路径

1. LLM 模式下连续游玩；
2. 某回合模型输出的场景被审查器连续 3 次驳回（当时的常见驳回原因："正文过短"）；
3. 触发兜底场景「（生成异常）+ 继续按钮」；
4. 玩家点击"继续"；
5. 观察：剧情跳到下一个节拍，当前节拍应有的内容从未出现 → 剧情断片。

### 根因分析

1. **【主因 · 节拍被吞】** 生成失败走兜底时，当前节拍仍被 `mark_done` 标记完成（`turn()` 中无条件结算 `self._active_beat`），下一次交互直接进入下一节拍——失败节拍的内容**永久丢失**，故事跳段；
2. **【诱因 · 提示词约束冲突】** v0.4.1 的"对白 5~6 行"与"全文 250~450 字"两条约束，模型未能同时满足，倾向写超短场景（95~112 字），审查器按"正文过短"（<150 字）连续驳回 3 次后触发兜底；
3. **【次要 · 倾向/数值混淆】** 模型把倾向维度（如 `curiosity`）误写进选项 `effects` 的 `stat.target`；审查器此前只校验 `world_updates` 的 stat 目标、漏检选项 effects，非法目标流入结算器后被静默丢弃（`choice_settle_partial`），选项效果丢失。

### 修复方式（当前方案 · v0.4.3）

1. **失败不吞节拍**：
   - 兜底场景增加 `_fallback` 标记；流水线检测到兜底时：不结算节拍、不写入记忆、不消耗回合，并把 `self._active_beat` 置空（`turn()` 的 `mark_done` 因此跳过）；
   - 导演 `next_instruction()` 新增逻辑：存在 `status=active` 的节拍时**优先返回该节拍**——玩家点「重试」后原地重新生成同一节拍，剧情内容不再丢失；
   - 兜底按钮文案由「继续」改为「重试」，避免误导。
2. **消除约束冲突**：重写"交互节奏与篇幅"铁律（对白 5~6 行 + 全文 ≥250 字 + 每行 15~60 字 + 用 2~4 行旁白补足）；审查器"正文过短"反馈改为显示真实阈值，并提示可用旁白行补足。
3. **堵住倾向/数值混淆**：提示词明确 `tendency`（倾向）与 `effects.stat`（数值）的边界；审查器新增**选项 effects 的 stat 目标校验**（与 world_updates 同规则），非法即驳回重写，不再流入结算器。

### 验证

- 回归测试：`tests/test_engine.py::TestGenerationFallbackRetry`——用 FailProvider 模拟 API 故障 → 兜底出现 → 点「重试」→ 重新生成**同一节拍** → 播放后才结算；主套件 48 项全绿；
- 真实 LLM 实测：连续 5 回合 0 兜底、0 降级，节拍 b1→b2→b4→b5→b7→b6 连续推进不断裂，场景 216~564 字、对白 4~8 行。

### 遗留风险 / 后续可改进（当前方案不一定最优，欢迎迭代）

- [ ] 兜底仍需玩家手动点「重试」：可改为失败时**自动重试**同一节拍（带指数退避），仅连续多次失败后才请求玩家介入，体验更顺滑；
- [ ] 重试上限目前统一为 3 次：可对"网络类错误"与"审查驳回"**分开计数**——网络抖动允许多次重试，审查驳回保持 3 次（避免烧 token）；
- [x] `active` 节拍的恢复依赖 `beat_status` 持久化：服务重启后 active 节拍会继续重试（存档恢复路径已覆盖，但未显式测试）——**2026-08-28 / v0.4.6 已由 BUG-002 的回归测试 `test_resume_after_restart_then_turn` 显式覆盖**；
- [ ] 更根治的方向：把"行数/字数"等约束从提示词搬到**后处理**（生成后按约束裁剪或压缩），减少对模型自觉性的依赖；
- [ ] 兜底前已流式推送的部分行，重试成功后前端整体重绘（当前依赖 linesMatch 对比处理）：可评估是否值得保留失败前的行、减少闪烁。

## BUG-002 服务重启后恢复存档的回合崩溃（前端无限卡"编剧正在书写"）

- **状态**：已修复
- **发现时间 / 版本**：2026-08-28 / v0.4.5（本地部署 v0.4.5 故事导图功能时暴露）
- **修复时间 / 版本 / 提交**：2026-08-28 / v0.4.6 / `1440d18`
- **关联迭代记录**：`docs/05-迭代文档.md` v0.4.6

### 现象

用户报告：点击选项后前端一直显示"编剧正在书写……"，没有任何文案生成，也没有报错。

服务端日志（uvicorn stderr）中每个失败的回合对应一条线程崩溃：

```
Exception in thread Thread-1:
  File "server/app.py", line 346, in work
    scene = p.turn(choice_index=body.choice_index, ...)
  File "engine/pipeline.py", line 158, in turn
    cur_beat = self._active_beat
AttributeError: 'Pipeline' object has no attribute '_active_beat'
```

### 复现路径

1. 启动服务，玩家开局并玩若干回合（会话落盘 `data/sessions/s_*.json`）；
2. **重启服务**（或会话因 LRU 淘汰被逐出内存）；
3. 玩家刷新页面恢复存档，点击任一选项；
4. 观察：前端永久卡在"编剧正在书写……"，服务端日志出现上述 `AttributeError`。

### 根因分析

1. **【主因 · 恢复路径属性缺失】** `Pipeline._active_beat` 只在 `_generate()` 里赋值，`__init__` 从未初始化。内存中新建的会话总是先 `start()` 再 `turn()`，属性被隐式补上，所以正常流程永不报错；但**从磁盘恢复的会话**直接进入 `turn()`，属性不存在 → `AttributeError`；
2. **【放大器 · 异常被线程吞掉】** NDJSON 流式回合跑在独立 worker 线程里，`work()` 只捕获 `ValueError/RuntimeError`——`AttributeError` 直接杀死线程，`queue.Queue` 永远收不到 `done`/`error` 事件，`StreamingResponse` 生成器永久阻塞在 `q.get()`，HTTP 连接悬空、前端无限等待；
3. **【诱因 · 触发条件罕见】** 生产服务长期运行、重启极少，会话几乎总在内存中，因此该 bug 长期潜伏——本地部署新版本需要重启服务时才暴露。

### 修复方式（当前方案 · v0.4.6）

1. **补初始化 + 恢复推导**（`engine/pipeline.py`）：
   - `__init__` 显式初始化 `_active_beat = None`；
   - 恢复的会话从 `beat_status` 推导当前 `active` 节拍，保证第一回合正确结算并推进；唯一例外：存档停在生成失败兜底场景（`current_scene._fallback`）时保持 `None`，重试仍重生成同一节拍（与 BUG-001 的"失败不吞剧情"语义一致）；
2. **流式 worker 兜底**（`server/app.py`）：`work()` 追加 `except Exception` 兜底——打印完整堆栈并回传 error 事件，前端显示"生成异常，请重试"并恢复上一交互点，任何未预期异常都不再导致流挂起；
3. **旧存档导图回填**（`engine/graph.py`，本次一并处理）：无导图字段的旧存档恢复时，从 `beat_status`+事件账本重建已完成节拍的节点与选项边，老玩家继续玩时故事导图不缺历史路线。

### 验证

- 回归测试：`tests/test_api.py::test_resume_after_restart_then_turn`（重启恢复 → 回合正常返回并推进到下一节拍）；`tests/test_graph.py::test_old_save_without_graph_fields_backfilled`（旧存档回填 b1→b2 + 选项边）；主套件 61 项全绿；
- 真实 LLM 实测：用户卡死会话 `s_a85db3cf` 恢复后，`POST /turn` 正常返回 8 个流式 line 事件 + done，节拍推进、场景生成正常；导图回填出 `b1 →(选项文案)→ b2`。

### 遗留风险 / 后续可改进（当前方案不一定最优，欢迎迭代）

- [ ] `_active_beat` 是内存态属性，本质是"恢复时从 `beat_status` 推导"的补丁：更根治的方向是**删除该属性**，`turn()` 一律以 `beat_status` 中 `active` 节拍为准（需同步梳理 BUG-001 的重试语义，确保兜底重试仍不吞节拍）；
- [ ] 流式 worker 的异常兜底只回传了消息，未携带结构化错误码：可扩展 error 事件为 `{type:"error", code, detail}`，前端按错误码区分"重试/换剧本/已结算"等处置；
- [ ] BUG-001 遗留风险中"重启后 active 节拍恢复未显式测试"一项，已由本次回归测试覆盖，可划掉。

## BUG-003 数值/事实变化提前触发（未到剧情点就结算）

- **状态**：已修复
- **发现时间 / 版本**：2026-08-28 / v0.4.6（玩家反馈 + 会话数据全量扫描）
- **修复时间 / 版本 / 提交**：2026-08-28 / v0.4.7 / 待提交（本次推送）
- **关联迭代记录**：`docs/05-迭代文档.md` v0.4.7

### 现象

玩家反馈：第一个选项里根本没有注意到有人消失，但选择"检查物品"后还是触发了"注意到有人不见了 → 理智值下降"，数值变化没有发生在真正的剧情点上。

会话数据佐证（`data/sessions/*.json` 事件账本）：

- 全库 522 个会话扫描：16 个会话的第一回合**选项 effects** 里挂了数值/事实变化；
- 典型污染（`s_a85db3cf`）：b1 选"问林sir为什么不觉得奇怪"→ 选项效果直接结算 `sanity -3` + 授予 `f_ledger_confirmed`——而该事实按宪法由 **b3 节拍完成时自动授予**（b1 时玩家还没见过名册）；
- 另一类提前触发：选项效果里出现"目睹乘客凭空消失"的理智值下降，而乘客消失是 b2 的剧情点。

### 复现路径

1. LLM 模式开局；
2. 在第一个节拍（剧情点尚未发生）选择任一选项；
3. 观察"✦ 影响"提示：理智值/事实在选项上提前结算（例："理智值 -5（目睹乘客凭空消失）"）；
4. 打开存档事件账本：选项 effects 的结算时间早于该剧情点对应的节拍。

### 根因分析

1. **【主因 · 模型提前剧透机制】** 编剧拿到节拍表与世界观的语境后，倾向把"后续节拍才发生的事件"提前挂到当前选项的 effects 上（悬疑题材尤其明显：发现异常 → 立刻挂理智值下降）；铁律 7 只要求"事实来自清单"，没有禁止"提前触发"；
2. **【防线缺失 · 节拍保留事实可被提前授予】** 宪法规定节拍 `grants` 的事实由引擎在节拍完成时自动授予，但审查器不校验 effects/world_updates 是否提前授予了**其他节拍**的保留事实（如 b1 选项授予 b3 的 `f_ledger_confirmed`），提前触发后续剧情解锁条件；
3. **【放大器 · 展示时机混淆】** 前端"✦ 影响"把"选项结算后果"与"新场景 world_updates"合并成一行、显示在新场景播放之前——即使数值变化是场景侧的正确结算，玩家也会把它归因到自己的选项上，观感上"数值没到剧情点就变了"。

### 修复方式（当前方案 · v0.4.7）

1. **审查器硬防线**（确定性、零成本）：effects/world_updates 授予**其他节拍**的保留事实 → 驳回重写（当前节拍冗余标注自己的保留事实放行，引擎落账幂等）；
2. **提示词强化**：铁律 7 明确"数值与事实标注必须严格对应本场/本选项直接发生的后果；本场没发生的事绝不标注；后续节拍的事件不得提前挂上"；
3. **一致性审查扩展**（复用既有调用）：world_updates 与 effects 中每条变化必须对应本场真实发生的事件，不符项以 `effect_unjustified` 驳回重写；
4. **前端分时展示**：`last_effects` 拆分为 `{choice, scene}`——"✦ 你的选择"在选择气泡后显示，"✦ 剧情推进"在本场剧情播完、出选项前显示；
5. **数据修复**：`s_a85db3cf` 回滚 b1 选项误挂的 `sanity -3` 与 `f_ledger_confirmed`。

### 验证

- 回归测试：`tests/test_engine.py::test_critic_rejects_premature_beat_grant`（提前授予驳回 / 本场冗余标注放行 / 玩家行为事实放行）；`tests/test_api.py` 断言首回合理智值变化落在 `last_effects.scene` 侧而非 `choice` 侧；主套件 62 项全绿；
- 真实 LLM 实测：新会话第一回合选"检查车门"→ 选项效果 = 好奇 +1、理智 -5（靠近车门感到不安，与行动直接相关）；场景效果 = 名册残页事实；无提前触发、无 `effect_unjustified` 降级。

### 遗留风险 / 后续可改进（当前方案不一定最优，欢迎迭代）

- [ ] 审查器只能硬拦"节拍保留事实"，**数值类**提前触发仍依赖提示词+LLM 一致性审查（软约束）：更根治的方向是把"哪些数值在哪些节拍允许变化"写进宪法（数值事件的剧情点白名单），审查器按表硬校验；
- [ ] 一致性审查只检查"本场是否发生"，不检查"发生得是否值得这个数值幅度"：可让审查同时输出"幅度是否过当"（如 -5 是否应为 -2），再决定驳回或只警告；
- [ ] 存量 LLM 会话的污染数据只手工修复了 `s_a85db3cf`：其余 15 个会话的历史数值仍含提前结算，如需精确统计可写一次性数据修复脚本回滚。
