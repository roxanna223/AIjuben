# 系统架构文档 v0.1（草案）

> 配套：01-PRD / 02-剧本Schema规范 / 04-样例剧本 / 07-工程化校验框架
> 核心思想：把整个系统想象成一个"AI导演组"——**剧本宪法是剧本，世界状态是场记，AI编剧是笔杆子，导演规划器是控场的人**。

## 1. 总体架构（四层模型）

```
┌─────────────────────────────────────────────────────────────┐
│                    Web 前端（人物对话 UI，零构建静态页）         │
│   逐句播放(点击/空格推进·自动播放) · 人物气泡/头像 ·            │
│   交互点选项+输入(仅交互点显示) · "✦影响"提示 · 路线复盘图        │
└──────────────────────────┬──────────────────────────────────┘
                           │ REST / SSE 流式
┌──────────────────────────▼──────────────────────────────────┐
│                   应用层 API（FastAPI）                       │
│   开局 · 回合提交 · 状态查询 · 复盘生成                        │
└───────┬──────────────────────────────────┬───────────────────┘
        │                                  │
┌───────▼──────────────┐      ┌────────────▼─────────────────┐
│  导演规划器 RouteDirector │      │   结算器 Ledger             │
│  选节拍/选人物/筛结局/锁支线 │      │   校验AI的world_updates     │
│  （确定性代码，非AI）       │      │   更新数值/倾向/事实/账本     │
└───────┬──────────────┘      └────────────┬─────────────────┘
        │                                  │
┌───────▼──────────────────────────────────▼─────────────────┐
│                 AI编剧流水线 Narrator Pipeline                │
│   ① 规划器prompt → ② 编剧生成场景 → ③ 审查器 → ④ 结构化输出    │
└─────────────────────────────────────────────────────────────┘
        │ 读/写
┌───────▼─────────────────────────────────────────────────────┐
│   存储：剧本宪法(静态JSON) · 世界状态 · 事件账本 · 三层记忆      │
│   SQLite（MVP）→ PostgreSQL；剧本与状态以JSON列存储             │
└─────────────────────────────────────────────────────────────┘
```

**分工铁律**：
- AI负责"写"（对白、选项、更新草案）；
- **确定性代码**负责"管"（节拍调度、数值结算、结局判定、禁忌硬查）——AI的 `world_updates` 必须经结算器审核才能落账，AI不能直接改库；
- **校验量表 ValidationScale**负责"裁"（数值/剧情出发点的工程化校验：数值只在声明的剧情点/幅度内变化、节拍保留事实不得提前授予、理由禁用词硬拦提前触发）——规则是数据、检查是插件、口径按剧本自动装配，构建/运行/审计三环境同一套量表，详见 `docs/07-工程化校验框架.md`。

## 2. AI编剧流水线（每轮一次）

```
用户选择/自由输入
   ↓
① 规划器（轻量调用，~500 token out）
  输入：宪法节拍表 + beat_status + 倾向向量 + 三层记忆摘要
  输出：本场节拍ID、出场人物、需推进/埋设的伏笔、给编剧的写作指令
        + 本场固定剧情锚点(fixed_plot：基础剧情细节+依据，标注"不得改写")
   ↓
② 编剧（主调用，~600 token out）
  输入：宪法(世界观/人物卡/关系/文风/禁忌) + 本场指令 + recent记忆全文 + 数值状态
  输出：SceneOutput（对话体dialogue行+选项+updates草案）
   ↓
③ 审查器（把关调用）
  检查：禁忌清单(content+story) · 事实一致性(与facts表核对) · 数值范围 ·
        dialogue结构(说话人必须在人物表内/旁白行精短/对白行数节奏) ·
        固定剧情锚点是否符合 · 是否承接玩家上一选择(choice_ignored) · 文风偏离
        + 变化类校验(数值/事实合法性、数值/剧情出发点绑定)由校验量表
          ValidationScale 承担(9条规则插件+情景化口径,error驳回/warn记账)
  不合格 → 带修订意见退回②重写（最多3次；仍失败 → 降级为"重试"按钮，
            节拍保持active不吞剧情，玩家点击后原地重生成同一节拍）
   ↓
④ 结算器落账 → 返回前端（对话行NDJSON流式逐行推送，前端逐句播放：打字机+
   点击/空格推进/自动播放；选项处暂停，选择影响以"✦影响"即时展示）
```

## 3. Prompt 组织方式

- **System Prompt（稳定，每局复用）**：宪法压缩版（世界观+人物卡+关系+文风+禁忌）+ 输出JSON格式说明 + 写作铁律。
- **User Message（每轮重组）**：导演指令 + 当前场景状态摘要 + 近期记忆 + 用户本次选择。
- **写作铁律**（示例）：
  1. 只写用户能看到的内容，禁止泄露NPC的secret；
  2. 不得违反禁忌清单，节拍未到不得剧透；
  3. 选项必须真实分化——至少一个选项会显著改变后续走向；
  4. 倾向标签必须如实标注每个选项的倾向含义。

## 4. 导演规划器（确定性代码）

每轮执行的逻辑（伪代码）：

```
1. 扫描 beat_status：
   - fixed 且未完成 → 最高优先
   - conditional 且 when 条件已满足 → 次高优先
   - optional 且倾向解锁条件满足 → 由规划器择机插入（每章≤1个）
2. 人物调度：好感度TOP2角色 + 当前节拍关联角色 → 建议出场名单
3. 结局筛选：重新计算 endings_viable；若只剩1个结局 → 规划器转入"收束模式"，
   提示编剧开始回收伏笔（防止烂尾）
4. 输出：导演指令（JSON）交给编剧
```

**路线分化从哪来**：节拍顺序/种类相同，但①条件节拍的触发与否不同；②可选支线不同；③编剧拿到的"人物态度"不同（好感低的人不会向你吐露秘密→拿不到关键事实→结局池收窄）。三个来源叠加，实现千人千线。

## 5. 数据存储

| 数据 | 存储 | 说明 |
|---|---|---|
| 剧本宪法 | 静态JSON文件/DB行 | 发布即定稿，按story_id索引 |
| 世界状态 | sessions表（JSON列） | 每回合落盘，支持断线续玩 |
| 事件账本 | events表（逐条） | 可追溯、可复盘、可做分析 |
| 三层记忆 | 世界状态内 | recent保持10场，超限压入摘要 |
| 成本埋点 | usage表 | 每轮token/模型/延迟，算ROI |

## 6. API 设计（MVP）

```
POST /api/stories/{story_id}/sessions       开局 → session_id + 开场
POST /api/sessions/{sid}/turn               提交选择 {choice, free_input?} → 下一场景(SSE)
GET  /api/sessions/{sid}/state              断线恢复/调试
GET  /api/sessions/{sid}/recap              结局后的路线复盘数据
```

## 7. 技术栈选型（建议）

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Next.js 14 + Tailwind | 对话流UI开发快，SSE流式展示成熟 |
| 后端 | FastAPI (Python 3.12) + Pydantic | Pydantic与JSON Schema天然契合（AI结构化输出的校验成本最低） |
| 模型 | **可插拔Provider**：DeepSeek（默认）/豆包/Qwen | 国产便宜+中文强；统一OpenAI兼容接口，可A/B切换 |
| 存储 | SQLite → PostgreSQL | MVP零运维，扩容平滑 |
| 内容安全 | taboos+审查器（自建）→ 可选接阿里云内容安全 | 先自建跑通，量起来再接商业API |
| 部署 | 单机Docker；前端Vercel/自有服务器 | MVP从简 |

> **MVP实现备注（2026-08 第2轮）**：Phase 1 前端先采用零构建静态页（`server/static/`，原生JS+CSS，由FastAPI托管），后端FastAPI已落地；Next.js迁移推迟到需要复杂交互/SSE流式调优时再做，API契约不变。

**不引入**：LangChain等重框架（MVP用官方SDK+自建流水线即可，降低复杂度）、向量数据库（三层记忆的摘要方案足够，Phase 3再评估）。

## 8. 成本模型（估算，待实测校准）

单场景 ≈ 规划器(1.5k in/0.2k out) + 编剧(3k in/0.6k out) + 审查器(2k in/0.3k out)
≈ **6.5k in / 1.1k out ≈ 1万token量级/场景**（按实际模型计价，当前国产模型下约 ¥0.01-0.02/场景）

- 一局约40-60场景 ≈ **¥0.5-1.2/局**（含重试与摘要压缩开销）
- 订阅定价的毛利空间足够；**必须做usage埋点**，每周盯单局成本曲线。
- 优化杠杆：①摘要压缩减少recent膨胀 ②审查器用小模型 ③缓存宪法System Prompt ④批处理（后续）。

## 9. 质量评测体系（科学性保障）

没有评测的AI叙事项目必然失控，从Phase 0就建三条线：

1. **自动指标**（每局自动算）：JSON解析成功率、审查器通过率、节拍踩点率、事实矛盾检出率、单局成本。
   - ✅ 已落地（2026-08 第3轮）：`metrics.py` + `GET /api/admin/metrics`，会话级埋点（时间戳/结局/节拍路径），自动计算并对照调研基线：第1章完读率≥60%、结局达成率≥50%、结局路线分化度≥3、平均会话时长≥15分钟；真实LLM用量埋点写入 `data/usage.jsonl`（token/延迟/成本）。
2. **金标准走查**（每个剧本配一组"预定选择序列"）：回归测试——同一选择序列重复生成N次，人工抽检质量漂移。
   - ✅ 已落地：Mock三路线走查（确定性）+ `scripts/llm_walkthrough.py` 真实LLM走查。
3. **人工小样本打分**（每剧本20局）：一致性/文风/惊喜度/选项质量/结局满意度，1-5分制，作为"剧本能否上架"的闸门。
   - ✅ 自动化替身已落地（2026-08 第6轮）：`scripts/judge_quality.py` LLM-as-judge 四维打分，多局随机走查可重复；真人抽检仍作为上线前交叉验证。
   - ✅ **LLM事实一致性审查器**：审查器第二道关（真实模型模式），每场生成后检查与既定事实的矛盾，发现即带反馈重写；矛盾未消除则标记不阻断。

## 11. Phase 0 概念验证的验收标准（下一步就要做）

- 单剧本（样例剧本JSON）跑通：开局→选择→生成→结算→节拍推进→结局判定的完整闭环；
- 连续30轮无JSON解析失败、无事实矛盾（金标准走查）；
- 10组不同选择序列，产出≥3条不同的结局路径；
- 单场景成本与延迟达标（首字延迟<3s）。
