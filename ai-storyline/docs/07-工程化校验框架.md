# 工程化校验框架（ValidationScale）设计文档

> 代码：`engine/validation.py` · CLI：`scripts/validate_content.py` · 测试：`tests/test_validation.py`
> 版本：v0.4.8（2026-08-28）· 配套文档：02-剧本Schema规范（`validation` 段）/ 03-系统架构 / 05-迭代文档

## 1. 这是什么（一句话定位）

**校验 AI 生成内容的"数值出发点/剧情出发点"的工程化工具**——把"数值与事实的变化必须发生在对应的剧情点上"这条原则，从散落在代码里的 if-else，沉淀为**规则是数据、检查是插件、口径按剧本自动装配**的可复用校验框架，并在构建期、运行期、审计期三种环境中以同一套量表执行。

## 2. 它解决什么问题（背景）

BUG-003（见 `06-Bug记录与修复.md`）：LLM 生成剧情时会把**后续剧情点才发生的事件提前挂到当前选项/场景上**——例如玩家在第一节拍选择"检查物品"（此时乘客尚未消失），选项效果却结算了"目睹乘客凭空消失"的理智值下降，甚至提前授予了本应由第三节拍完成时才自动授予的事实。全库审计实测：历史会话中 midnight-train 190 个会话 316 条、rule-tower 79 个会话 160 条此类违规。

**框架要回答的问题**：一条数值/事实变化，发生在**哪个剧情点**、**幅度是否合规**、**理由是否越界**、**来源是否合法**——这些必须能被确定性代码裁决，而不是只靠提示词"希望 AI 自觉"。

## 3. 能力边界（能做 / 不做）

| 范畴 | 能力 |
|---|---|
| ✅ **结构性校验** | 数值目标必须已声明（stat 目标 ∈ 宪法数值ID）；倾向维度必须合法；事实ID必须来自事实清单；更新类型必须是 stat/tendency/fact/close_fact |
| ✅ **数值出发点** | 数值变化必须发生在声明允许的节拍（白名单）；单次变化幅度不超上限；大额变化必须携带原因；理由中的"剧情点外关键词"硬拦（如 b1 的理由出现"消失"→ 提前触发，驳回）；零增量更新提示清理 |
| ✅ **剧情出发点** | 节拍保留事实（`beats[].grants`）不得在其他节拍提前授予；普通事实必须在其声明的节拍/来源（scene/choice/beat_grant）下授予 |
| ✅ **语义一致性（LLM判定注入）** | 每条变化是否对应本场真实发生的事件（`effect_unjustified` → 驳回重写）；幅度是否与剧情严重程度匹配（`magnitude_issues` → 警告记账） |
| ✅ **三环境复用** | 构建期校验 mock 脚本（防坏内容进生产）；运行期每场 AI 输出即时校验；审计期离线扫描历史会话追查违规 |
| ✅ **审计与记账** | 每场生成后 `validation_report`（verdict/score/逐条 finding）落事件账本，可事后复盘、可评测 |
| ✅ **插件扩展** | 新校验维度 = 注册一个 check 函数 + 在规则表登记，框架代码零改动 |
| ❌ **不改写内容** | 校验只给出"驳回+修订意见"，绝不自行修改 AI 输出（铁律：AI 只写、代码只管） |
| ❌ **不做文学质量评判** | 文风/惊喜度/可读性由 `scripts/judge_quality.py`（LLM-as-judge 四维打分）负责，不在本框架范围 |
| ❌ **不负责内容安全红线** | 禁忌词/敏感词检查仍在审查器 Critic 的形态检查里（两者并存，职责不同） |
| ❌ **不保证语义 100% 确定性** | 语义类判断依赖一致性审查 LLM 的判定（框架只负责记账与执行裁决）；确定性部分才是硬保证 |
| ❌ **不自动修复历史数据** | 审计期只报告违规，不回滚历史会话数值（如需修复另写一次性脚本，参照 BUG-003 的手工回滚） |

## 4. 架构

### 4.1 数据流（三种运行环境，同一套量表）

```
                 ┌─────────────────────────────────────────────┐
                 │        ValidationScale（量表装配层）           │
                 │  rules 规则表 = 内置插件 + 剧本 validation 覆盖 │
                 │  plot_points / fact_origins = 情景化口径       │
                 └───────────────────────┬─────────────────────┘
                                         │ check_change(ctx)
        ┌────────────────┬───────────────┴───────────────┬────────────────┐
        │                │                               │                │
   ┌────▼─────┐    ┌─────▼──────┐                  ┌──────▼──────┐  ┌──────▼──────┐
   │ 构建期    │    │ 运行期      │                  │ 审计期       │  │ 语义(LLM)   │
   │ mock场景  │    │ AI生成场景  │                  │ 历史事件账本 │  │ 一致性审查   │
   │ scene→ctx │    │ scene→ctx  │                  │ event→ctx   │  │ 判定→记账   │
   └────┬─────┘    └─────┬──────┘                  └──────┬──────┘  └──────┬──────┘
        │                │                               │                │
        └────────────────┴───────────┬───────────────────┴────────────────┘
                                     ▼
                          ValidationReport（结构化报告）
                    verdict(rewrite/accept_with_warnings/pass)
                    score(0~100) · errors · warnings · 逐条 finding
                     ↓                ↓
               error → 驳回重写    warn → 接受并落 validation_warn 记账
```

- **构建期**：`scripts/validate_content.py --story X --mock` 对 mock 脚本每个场景跑量表，任一 error 即失败（CI/测试门槛）。
- **运行期**：流水线审查器 `Critic.review()` 委托量表做变化类校验——error 消息并入驳回意见（复用既有"带修订意见重写，最多 3 次"环）；warn 不阻断，场景落账后记 `validation_warn`；每场生成后记 `validation_report`。
- **审计期**：`scripts/validate_content.py --story X --sessions DIR` 把会话事件账本中的 stat/tendency/fact/close_fact 事件重建为变化上下文，逐条裁决，输出违规清单。
- **语义判定**：一致性审查 LLM（每场已有一次调用，零新增成本）输出 `contradictions`（含 `effect_unjustified` → error 走重写）与 `magnitude_issues`（→ warn 记账），由流水线喂入报告。

### 4.2 核心概念

| 对象 | 说明 |
|---|---|
| `ChangeCtx` | 校验的**原子单位**：一次变化（kind=stat/tendency/fact/close_fact）+ 目标 + 幅度 + 原因 + 来源（scene/choice/event/beat_grant）+ 所在节拍。三种环境的数据都被归一成它 |
| `Finding` | 单条判定结果：rule_id + 维度 + 严重度(error/warn) + 状态(fail/warn) + 详情 |
| `ValidationReport` | 一次校验的完整报告：findings 列表 + 每规则检查次数 + `verdict()` + `score()`（100 − 20×errors − 5×warnings，下限 0）+ `to_dict()` |
| 规则插件 | `fn(scale, ctx) -> Optional[Finding]`：违规返回 Finding、通过返回 None、不适用返回 None；规则表决定其 id/维度/默认严重度/参数 |
| 情景化口径 | 宪法 `validation` 段的 `plot_points`（数值出发点）与 `fact_origins`（剧情出发点）声明，量表构造时自动装配 |

### 4.3 插件机制（新增校验维度三步）

```python
# 1) 写一个 check 函数（engine/validation.py）
def _my_new_check(scale, ctx):
    if ctx.kind != "stat":
        return None                       # 不适用
    if <违规条件>:
        return Finding("my_new_check", "数值出发点", "error", "fail",
                       "数值 %s 违反XX规则" % ctx.target, ctx.target)
    return None

# 2) 在 BUILTIN_CHECKS 登记
BUILTIN_CHECKS = {..., "my_new_check": _my_new_check}

# 3) 在 DEFAULT_RULES 声明规则（剧本可用 validation.rules 覆盖严重度/参数）
DEFAULT_RULES += [{"id": "my_new_check", "dimension": "数值出发点",
                   "severity": "error", "check": "my_new_check",
                   "desc": "...", "params": {...}}]
```

要点：`dynamic_severity: True` 的规则（如 `reason_required` 按幅度决定 warn/error）以插件判定为准，不被规则表严重度覆盖。

## 5. 内置规则清单（9 条，五个维度）

| 规则ID | 维度 | 严重度 | 说明 | 可配置 |
|---|---|---|---|---|
| `update_type_valid` | 剧情合法性 | error | 更新类型必须在 stat/tendency/fact/close_fact 内 | — |
| `stat_target_defined` | 数值合法性 | error | stat 目标必须是宪法声明的数值ID | severity |
| `tendency_dim_defined` | 数值合法性 | error | 倾向维度必须是宪法五维之一 | severity |
| `fact_declared` | 剧情合法性 | error | 事实ID必须来自宪法事实清单 | severity |
| `zero_delta_forbidden` | 数值出发点 | warn | 变化量为 0 的 stat 更新无实际效果 | severity |
| `reason_required` | 数值出发点 | 动态 | stat 变化应携带原因；幅度 ≥ `min_error_delta`(默认10) 缺失原因 → error，否则 warn | severity/params |
| `beat_grant_not_premature` | 剧情出发点 | error | 节拍保留事实不得在其他节拍提前授予（本场冗余标注自己保留事实放行，引擎落账幂等） | severity |
| `plot_point_gate` | 数值出发点 | error | 按 `plot_points` 声明：节拍白名单/幅度上限/理由禁用词 | 见 §6 |
| `fact_origin_gate` | 剧情出发点 | error | 按 `fact_origins` 声明：事实的节拍/来源合法性 | 见 §6 |

## 6. 情景化口径配置（宪法 `validation` 段）

```json
"validation": {
  "plot_points": {
    "sanity": {
      "allow_at": ["b1", "b2", "b3", "b4", "b5", "b6", "b7"],
      "max_abs_delta": 30,
      "forbid_reason_hints": {
        "b1": ["消失", "不见了", "失踪", "没影"],
        "b3": ["消失", "不见了", "失踪", "没影"]
      }
    },
    "trust_lin": {"allow_at": ["b1", "b2", "b3", "b4", "b5", "b6", "b7"],
                  "max_abs_delta": 15}
  },
  "fact_origins": {
    "f_ledger_seen": {"beats": ["b2", "b3"], "via": ["scene", "choice"]},
    "f_escaped":    {"beats": ["b6"], "via": ["choice"]}
  },
  "rules": [{"id": "reason_required", "severity": "error",
             "params": {"min_error_delta": 10}}]
}
```

| 字段 | 含义 |
|---|---|
| `plot_points.<target>` | 目标为数值ID或倾向维度。`allow_at` 允许变化的节拍白名单（缺省=不限制节拍）；`max_abs_delta` 单次变化幅度上限；`forbid_reason_hints.<beat>` 该节拍理由中禁止出现的剧情点外关键词（命中即判定"提前触发"） |
| `fact_origins.<fact>` | `beats` 允许授予该事实的节拍；`via` 允许的来源（scene/choice/beat_grant）。节拍 `grants` 保留的事实由引擎自动授予，不受此表约束 |
| `rules` | 覆盖内置规则的 severity/params（error=驳回重写，warn=接受并记账） |

**缺省行为**：目标未声明口径 → 对应门规则跳过，只受通用规则约束（旧剧本零影响）。宪法加载时校验该段所有引用（规则ID/数值/节拍/事实/来源枚举），引用非法直接拒绝加载。

当前两个剧本均已配置：理智值/信任的白名单+幅度上限+b1/b3 理由禁用"消失"类词（午夜列车）；违规次数限幅 1（规则楼）；名册/怀表/结局类事实的节拍与来源声明。

## 7. 使用指南

### 7.1 构建期（上线前校验内容）

```bash
.venv/bin/python scripts/validate_content.py --story midnight-train --mock
# 输出每场 verdict/score/逐条 finding；exit 1 = 存在 error（CI 可挂）
```

### 7.2 运行期（无需操作，自动执行）

流水线每场 AI 生成后自动校验；通过会话事件账本观察：

```bash
# 在会话JSON的 event_log 里：
# {"type": "validation_report", "payload": {"beat": "b2", "verdict": "pass",
#   "score": 100, "errors": 0, "warnings": 0}}
# {"type": "validation_warn", "payload": {"beat": "b2", "rule": "reason_required", ...}}
```

### 7.3 审计期（离线追查历史会话）

```bash
.venv/bin/python scripts/validate_content.py --story midnight-train \
    --sessions data/sessions
# 输出：每个存在违规的会话 + 逐条 ✗/△ finding + 汇总（error/warn 数）；exit 1 = 有违规
```

审计的节拍归属规则：turn 内 `beat_done` 事件**之前**的结算归属于该完成节拍（选项后果），**之后**的归属于该回合新激活节拍（场景剧情）。

### 7.4 开发新校验维度

按 §4.3 三步注册；同时需补三类测试（`tests/test_validation.py` 范式）：违规检出 / 合规放行 / 两个剧本 mock 构建期零 error 回归。

### 7.5 报告解读

- `verdict=rewrite`：存在 error，审查器驳回重写（最多 3 次后降级兜底）；
- `verdict=accept_with_warnings`：仅 warn，场景照常落账，警告留痕供复盘；
- `score`：0~100，100 为全过（每条 error 扣 20、warn 扣 5），供批量评测比较。

## 8. 已知限制与设计取舍

1. **语义判断依赖 LLM**：确定性规则硬拦"出处/幅度/关键词"，但"这条变化是否真的在本场发生了"仍需一致性审查 LLM 判定（复用既有调用，零新增成本）；LLM 判定失败时降级为不阻断；
2. **审计期的节拍归属是近似**：依据 turn 与 beat_done 位置的映射，极端多事件同 turn 场景可能归属偏差（历史审计用途，可接受）；
3. **理由关键词是启发式**：`forbid_reason_hints` 按关键词硬拦，可能误伤修辞性表述——命中即驳回重写，宁可误拒不放过（重写成本远低于剧情点错乱）；
4. **动态严重度规则不响应剧本覆盖**：`reason_required` 等按幅度定级的规则以插件判定为准；
5. **只审计不修复**：历史会话的违规只报告（BUG-003 曾手工回滚一个会话作为示范）；
6. **未声明 = 不校验**：新增数值/事实若忘记声明口径，出发点门自动跳过——依赖宪法校验与构建期测试兜底（新事实建议同时声明 `fact_origins`）。
